# ZooKeeper Performance Analysis — SPE Project, Stage I (Group 18)

Scalability study of Apache ZooKeeper 3.9 on ensembles of 1, 3 and 5 servers:
a closed-loop read/write benchmark, a Universal Scalability Law (USL) fit per
ensemble size, a request-pipeline/bottleneck analysis, a YCSB cross-check, a
leader-failover test and a network-delay (chaos) experiment.

Everything runs in Docker with plain `docker run`. Docker Compose is not used,
as the project brief requires, so the same scripts carry over to the
multi-machine deployment of Stage II.

The report is `report.tex` (LNCS). The commit to evaluate is the one given in the report.

### Earlier Python data

The first sweep used `benchmark.py` (Python/kazoo). YCSB reached ~11.9k ops/s on
the same 3-node ensemble where the Python client saturated at ~600 ops/s: the
GIL serializes the client threads, so that sweep measured the load generator
more than ZooKeeper. `java-benchmark/` is a port with the same CLI, workload
and CSV schema, and its data (`results_java.csv`) is what the report uses.
The Python files are kept for traceability. `results.csv` contains two
N=1 sweeps that disagree with each other (the second is contaminated), so do
not fit it as-is.

## Demo: 3 servers, 10 clients

About two minutes end to end. Uses host ports 2181–2183 and 8081–8083.

```bash
# 1. Build the load generator (once)
(cd java-benchmark && mvn -q -DskipTests package)

# 2. Start a 3-node ensemble and wait for leader election
./scale_ensemble.sh start 3
./scale_ensemble.sh wait 3
for i in 1 2 3; do echo -n "zk$i: "; docker exec zk$i zkServer.sh status 2>&1 | grep Mode; done

# 3. Run 10 concurrent clients, 30% writes, 10 s measured after 2 s warmup
java -jar java-benchmark/target/zk-benchmark-1.0-SNAPSHOT.jar \
  --hosts 127.0.0.1:2181,127.0.0.1:2182,127.0.0.1:2183 \
  --ensemble-size 3 --clients 10 --write-ratio 0.3 \
  --duration 10 --warmup 2 --output demo.csv
#   -> [done] throughput=... ops/s  p50=...ms p95=...ms p99=...ms  errors=0
#   one CSV row is appended to demo.csv

# 4. Optional: kill the leader and check the ensemble keeps serving
docker kill zk<leader-id>
docker logs zk<other-id> 2>&1 | grep "LEADER ELECTION TOOK"
java -jar java-benchmark/target/zk-benchmark-1.0-SNAPSHOT.jar \
  --hosts 127.0.0.1:2181,127.0.0.1:2182,127.0.0.1:2183 \
  --ensemble-size 3 --clients 10 --duration 10 --warmup 2 --output demo.csv

# 5. Tear down
./scale_ensemble.sh stop
```

Change the ensemble size by passing `5` instead of `3` and listing ports
`2181`–`2185` in `--hosts`. For a fully manual deployment with explanations of
every `docker run` flag, see `zookeeper-setup-guide.md`.

## Reproducing the report

```bash
./run_java_experiments.sh                          # default sizes 3 5
ENSEMBLE_SIZES="1 3 5" ./run_java_experiments.sh   # full grid used in the report (~15 min)
python3 usl_fit.py --input results_java.csv --output-dir usl_plots_java \
    --combined-plot usl_java_fit.pdf               # Table 1 + Fig. 1
```

YCSB, the chaos experiment and the failover measurement are described step by step in `RUNBOOK.md`.

### Benchmark parameters

| Flag | Default | Meaning |
|---|---|---|
| `--hosts` | (required) | connect string. List every server so sessions spread across the ensemble |
| `--ensemble-size` | (required) | recorded in the CSV, used to group the USL fit |
| `--clients` | (required) | concurrent sessions, one thread each, closed loop, synchronous calls |
| `--write-ratio` | 0.3 | probability that an op is `setData` (otherwise `getData`) |
| `--duration` / `--warmup` | 30 / 5 s | measured window / discarded warmup, starting once all sessions are connected |
| `--pool-size` / `--payload-bytes` | 200 / 128 | pre-created znodes, uniformly chosen per op / value size |
| `--output` | results.csv | CSV to append the result row to |
| `--raw-output` | — | optional JSONL with every operation's latency |

## Known limitations

- Single host: the load generator and all servers share CPU and disk.
- One run per grid point, and the sweep stops at 80 clients.
- `mntr` is sampled at about 1 Hz.
- The workload is `get`/`set` on a fixed pool. It does not cover `create`, watches or ephemerals.
