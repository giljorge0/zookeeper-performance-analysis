\section{Corrections to the Stage I Measurements}
\label{sec:corrections}

Before the Stage II experiments we re-examined the Stage I data and found three problems. We report them because
they change two conclusions of the Stage I report.

\paragraph{The load generator logged every operation.}
The same configuration (3 servers, 20 clients, 30\% writes) reached about 6{,}400 ops/s in the Stage I sweep but
16{,}000--18{,}000 ops/s in a short demo run. A controlled comparison of the two builds showed that the jar used for the sweep
printed about 145{,}000 lines in a 15\,s run, roughly one per operation: the shaded jar contained Logback, whose
default configuration logs the ZooKeeper client at DEBUG level, so all client threads queued on the console.
Redirecting the output to a file raised throughput to 8{,}000--10{,}000 ops/s, and a quiet client reached
16{,}000--34{,}000 ops/s. The fix is a one-line Logback configuration that turns logging off; the experiment runner
now also aborts a run if the client prints more than a few lines.
This invalidates the Stage I interpretation of $\alpha$. The Stage I fits gave the same $\alpha\approx0.23$ for 1, 3 and
5 servers, and we concluded that the contention was server-side but not specific to Zab. A client-side
serialization point looks exactly like that, because it does not depend on the number of servers; the constant $\alpha$
was most likely an artifact of the client. With the quiet client the fitted $\alpha$ is 0.025, 0.088 and 0.112 for
1, 3 and 5 servers, and the standalone server no longer saturates within 80 clients (29{,}000 ops/s). We
withdraw the Stage I claim and re-measure $\alpha$ in Section~\ref{sec:usl}.

\paragraph{Run-to-run variation on a laptop is large.}
Nine runs of the identical configuration (3 servers, 20 clients) gave between 18{,}000 and 24{,}000 ops/s, with a
downward drift over the sequence, and neither the JVM heap flags nor the metrics collector changed the result.
The Stage I sweep used one run per point in order of increasing load, so drift and load were confounded, and the
differences between the three fitted curves are within this noise. This is why Stage II uses dedicated virtual
machines, several replicates and a randomized run order.

\paragraph{The network-delay experiment was misreported.}
The ``$27\times$'' collapse of throughput under a 20\,ms delay compared the delayed run with the old Python
baseline. Against the corrected Java baseline, single-client throughput falls from 2{,}386 to 20.6 ops/s
($116\times$), whereas at 80 clients it falls only from 16{,}255 to 1{,}709 ops/s ($9.5\times$). Throughput per
client is constant at about 21.5 ops/s for every client count, that is, $1/48.5$\,ms: a closed-loop client completes one
operation per round trip, and $N$ clients in parallel complete $N$ operations. The fitted $\alpha$ and $\beta$ are
near zero because the delay hides the server entirely, as discussed in Stage I. The per-operation latencies give a
direct view of the write pipeline: the median read takes 22.7\,ms, one delayed hop (the reply), whereas the
median write takes 106\,ms, about five delayed hops (forward to the leader, proposal, acknowledgment, commit,
reply). This is consistent with the pipeline of Section~2 of Stage I, for clients attached to a follower.
