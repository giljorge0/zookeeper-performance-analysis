\begin{abstract}
ZooKeeper serves reads at any server, but every write goes through one leader and a quorum. We measured the cost of this write path on Google Compute Engine with a $2^{6-1}$ factorial experiment, Universal Scalability Law curves at three write ratios and five eBPF probes. The share of writes and the number of clients explain most of the variation, and turning \texttt{fsync} off helps at light load but hurts at saturation. With writes the curves show contention but no crosstalk, and the CPU the leader spends per operation near saturation matches the bottleneck demand the fit implies. We also found that a logging client had distorted our Stage I results.
\end{abstract}

\section{Introduction}

Apache ZooKeeper is a coordination service used by Kafka, HBase and Hadoop for leader election, configuration and locks~\cite{hunt_zookeeper,apache_zookeeper_overview}. Its replication protocol, Zab~\cite{zab_junqueira}, makes reads and writes behave very differently: a read is answered by the server the client is connected to, while a write goes to the leader, is logged and acknowledged by a majority and only then committed. Reads should therefore scale with the number of servers and writes should not, and the write pipeline is where we look for the limits of scalability. We chose ZooKeeper because this single-leader design is shared by many coordination and consensus systems, and because it exposes per-stage timers that let us check a model against the pipeline itself.

Stage I measured one laptop with Docker and fitted the Universal Scalability Law (USL)~\cite{gunther_usl_dsconf,gunther_book}. For Stage II we first found a client-side artifact in that data (Section~\ref{sec:stage1}). On dedicated virtual machines we then ran a fractional factorial experiment (Sections~\ref{sec:design}--\ref{sec:factorial}), fitted USL curves at 0, 30 and 50\% writes with ZooKeeper's per-stage timers (Section~\ref{sec:usl}), and looked inside the leader with eBPF (Section~\ref{sec:ebpf}).

\section{System Description}
\label{sec:system}

ZooKeeper keeps a tree of small data nodes (znodes) in memory. Clients read and write whole znodes of at most 1\,MB, can set one-time \emph{watches} that notify them of a change, and can create \emph{ephemeral} znodes that disappear when their session ends. Each client holds a session with one server, kept alive by heartbeats. Every change is appended to a transaction log, and the in-memory tree is written to a snapshot from time to time. With $N=2f+1$ voting servers, the group elects a \emph{leader}, survives $f$ failures and stops accepting writes when no majority is reachable~\cite{zab_junqueira}. \emph{Observers} also receive the committed writes, but they do not vote. Writes are linearizable, while reads are only sequentially consistent per session and may be slightly stale. That relaxation is what lets a follower answer a read alone~\cite{hunt_zookeeper}. Figure~\ref{fig:pipeline} shows both paths.

Inside the leader, a write passes a chain of processors. Request preparation, a single thread, validates it and assigns its zxid. The log-sync stage, also a single thread, appends it to the log and calls \texttt{fsync}, and it writes every request queued at that moment in one batch, which is called group commit. Once a majority has acknowledged, the commit stage applies the write. The followers run the same log-sync stage before they acknowledge. Reads go through the commit stage too, and a read waits there while a write of the same session is pending. A read thus costs one hop, while a write needs a forward, a proposal, a log write and \texttt{fsync} on every follower, the acknowledgments and a commit.

\section{Stage I}
\label{sec:stage1}

In Stage I the same configuration (3 servers, 20 clients, 30\% writes) gave 6{,}364 ops/s in the sweep and 14{,}832 ops/s when we repeated it later. The jar used for the sweep bundled Logback, and its default configuration logs the ZooKeeper client at DEBUG level. It printed about 145{,}000 lines in a 15\,s run, more than one per operation, and every client thread ended up waiting on the console. A one-line Logback configuration fixes this, and the runner now aborts any run in which the client prints more than a few lines. Those fits had given the same contention coefficient ($\approx0.23$) for 1, 3 and 5 servers, and we had concluded that the contention was on the server side but not caused by Zab. A bottleneck in the client gives exactly that picture, because it does not depend on the number of servers. With the quiet client the coefficient became 0.025, 0.088 and 0.112 for 1, 3 and 5 servers. On the laptop all servers shared one CPU, so every extra server added load to the same machine, which is not the case with separate cloud machines. Repetitions of one variant on the laptop also differed by up to a factor of two. For these reasons Stage II uses separate machines for client and servers, replicates and a randomized order. The Stage I experiments we did not repeat (YCSB, leader failover, injected network delay) are summarized in Appendix~\ref{app:stage1} as context only.

\section{Testbed and Methodology}
\label{sec:method}

\paragraph{Deployment.} All Stage II runs use Google Compute Engine in one zone (europe-west1-b). The load generator has its own n2-standard-8 machine (8 vCPUs, 32\,GB), and every ZooKeeper server has an n2-standard-2 (2 vCPUs, 8\,GB). Each server has two extra 20\,GB disks, one pd-balanced and one pd-ssd, formatted with ext4. The transaction log goes on one of them according to the factor \emph{log disk}, while snapshots stay on the boot disk. Before each block of runs the servers are stopped, their data is erased and they are restarted with the new configuration. Because a wrong setting would silently spoil a whole block, the runner then reads the \texttt{forceSync} flag and the log directory back from every server before the first run.

\paragraph{Load generator.} A Java client opens one ZooKeeper session per simulated client, and the connect string spreads the sessions over all servers. Each client runs a closed loop of synchronous calls with no think time. In every iteration it picks one of 200 znodes at random and sends a \texttt{setData} with probability equal to the write ratio, or a \texttt{getData} otherwise. Operations that start in the first 5\,s are executed but not recorded, which keeps JIT compilation and cold caches out of the measurement, and every series starts with a discarded run. After that, a factorial run measures 20\,s and a USL run 30\,s. Even the slowest factorial run completed more than 30{,}000 writes, so its 99th percentile rests on over 300 samples, and since all latencies are kept, the percentiles are exact. The client's CPU stayed below 47\% in every factorial run and below 28\% in the USL runs with writes. Before the experiments we set 70\% as the level above which we would discard a run. This is a rule of thumb rather than a derived value, since queueing inside the client grows as $1/(1-U)$ at any load and a busier client always says less about the servers.

\paragraph{ZooKeeper's per-stage timers.} The \texttt{mntr} command reports a count and a sum per stage (queue times, \texttt{fsync} time, batch size, time to quorum acknowledgment, commit to applied). Snapshots of every server before and after a run give the mean of that run as the ratio of the differences. The \texttt{fsync} timer truncates each call to whole milliseconds, so the \texttt{fsync} is also measured with eBPF.

\paragraph{Threats to validity.} The virtual machines share physical hosts with other tenants. Replicates and the random order spread that noise over all treatments, but they do not remove it, and two replicates of the same factorial run differ by 11\% at the median and by up to 48\%. Sessions are placed on a random server, so the leader's share of the sessions changes from run to run. In the extra USL curves, where we recorded it, the share averaged a third but ranged from 19\% to 44\% at 8--16 clients. Finally, \texttt{forceSync=no} is unsafe in production, and we use it only as a probe.

\paragraph{Parameters and metrics.} Table~\ref{tab:params} lists the fixed parameters and Table~\ref{tab:factors} the factors. The primary response is throughput (successful operations per second), the quantity the USL models. The secondary response is the 99th-percentile write latency, because a coordination service sits on the critical path of other systems. We do not use the mean latency as a separate response: in a closed loop without think time Little's law gives the mean response time $R=N/X$, so it carries no information beyond throughput. Read latency is recorded and reported, but reads do not enter the write pipeline. Failed operations (there were none) and the client's CPU are recorded as validity checks.

\paragraph{Factors and levels.} Each factor tests one guess about where a write spends its time (Table~\ref{tab:factors}). The two client levels, 10 and 160, come from the Stage I curve. On the new testbed 10 clients already run at 74\% efficiency (Section~\ref{sec:usl}), so in practice the levels are moderate load and deep saturation. For the write ratio, Hunt et al.\ give 2:1 to 100:1 read-to-write ratios as ZooKeeper's target workloads~\cite{hunt_zookeeper}. A write ratio of 0.1 lies inside that range, and 0.5 loads the write path well beyond it.

\paragraph{Design.} We use the half fraction $2^{6-1}$ with $F=ABCDE$ (defining relation $I=ABCDEF$)~\cite{jain_book}. It has resolution VI: main effects are aliased with five-factor interactions and two-factor interactions with four-factor ones, so all six main effects and fifteen two-factor interactions are estimated from 32 runs per replicate if interactions of order four and higher are negligible. Like any $2^k$ design, this assumes each factor's effect points the same way across its range. A quarter fraction would have resolution IV and alias two-factor interactions in pairs, which is exactly what three of our hypotheses (H2--H4, listed below) are about. Table~\ref{tab:sign} is the sign table: the full $2^5$ table of A--E with $F$ as the product of the other five columns. Two replicates give 64 runs and 32 degrees of freedom for error, which is what the credit allowed. With the measured error this gives intervals of $\pm0.015$ on each $\log_{10}$ effect, so a change of about 7\% between levels is detectable.

\paragraph{Restricted randomization.} A, D and F need a rebuild of the servers, which takes several minutes. Fully randomizing them would have meant 64 rebuilds, so we grouped the runs that share their levels into blocks of four (eight blocks per replicate, 16 rebuilds in total). The block order is randomized in each replicate, the run order inside each block as well, and the plan was generated with a fixed seed before the first run. The whole-plot contrast ADF is aliased with the subplot interaction BCE, so BCE is confounded with the blocks. Grouping runs this way makes the experiment a split-plot design. A, D and F change only from one block to the next, so for them a block, not a run, is one independent observation, and testing them against the run-to-run error alone would overstate their precision. We therefore test all effects against the pooled run error and, in addition, the seven whole-plot contrasts (A, D, F, AD, AF, DF, ADF) against a whole-plot error estimated from the 16 block means (replicate $\times$ treatment, $(2-1)(8-1)=7$ degrees of freedom).

\paragraph{Analysis.} With $s_{ij}$ the sign of run $i$ for effect $j$, $\bar y_i$ the mean of the $r=2$ replicates and $n=32$, the effect is $q_j=\frac1n\sum_{i} s_{ij}\bar y_i$, with $SS_j=nrq_j^2$, $s_e^2=\sum_{i,k}(y_{ik}-\bar y_i)^2/(n(r-1))$ and the interval $q_j \pm t_{[0.975;\,n(r-1)]}\,s_e/\sqrt{n r}$. Effect $j$ explains $100\,SS_j/SST$ percent of the variation. Since 31 effects tested at 95\% would give about two false positives by chance alone, we rank effects by their share of the variation instead of relying only on significance. When $y_{\max}/y_{\min}>10$ we analyse $\log_{10}y$ (residual plots in Appendix~\ref{app:residuals}). Before using the analysis scripts on the measurements, we ran them on synthetic data with known effects.

\paragraph{Hypotheses.} From the structure of the write pipeline (Section~\ref{sec:system}) and the quiet-client Stage I runs we expected:
\textbf{H1}: turning \texttt{fsync} off (D) raises throughput and lowers the write p99.
\textbf{H2}: that benefit grows with the write ratio (B$\times$D), since reads never touch the log.
\textbf{H3}: a faster log disk (F) helps only while \texttt{fsync} is on (D$\times$F).
\textbf{H4}: five servers (A) lower throughput and raise the write p99, mostly through writes (A$\times$B).
\textbf{H5}: the number of clients (C) has the largest main effect on throughput.

\section{Results}

\subsection{Factorial experiment}
\label{sec:factorial}

All 64 runs completed without errors. Throughput ranged from 5{,}335 to 81{,}088 ops/s and the write p99 from 1.2 to 61\,ms. Both ratios exceed 10, and the residuals of the additive model widen with the predicted value, so both responses are analysed on $\log_{10}$, where the residuals look homogeneous and roughly normal (Fig.~\ref{fig:residuals}). Effects are then multiplicative factors (Table~\ref{tab:effects}); all shares of variation below are of the $\log_{10}$ response. The error explains 2.1\% (throughput) and 1.3\% (p99), small next to factors that change throughput up to fifteen-fold even though replicates differ by about 11\%.

\paragraph{Throughput.} The write ratio (B) has the largest effect: going from 10\% to 50\% writes divides throughput by 2.9 (60\% of the variation). If a read costs the servers $r$ and a write $w$, a throughput ratio $\rho$ gives $(0.9r+0.1w)/(0.5r+0.5w)=\rho$. This holds only when server capacity sets throughput, that is, at 160 clients, where $\rho=0.32$ and $w\approx12r$: a write costs the system about twelve reads, an aggregate figure because reads are spread over all servers while writes load the leader most. The number of clients (C) comes second ($\times1.98$, 26\%), and 4\,KiB payloads (E) cost 26\% of throughput (5\%).

The largest interaction is clients $\times$ \texttt{forceSync} (C$\times$D, 3.6\%, Fig.~\ref{fig:pareto}). With 10 clients, turning \texttt{fsync} off raises throughput from 12{,}381 to 17{,}150 ops/s (geometric means, +39\%), but with 160 clients it lowers it from 31{,}776 to 26{,}270 ops/s ($-17\%$). This reversal holds in every cell, and at 160 clients the ratio without and with \texttt{fsync} is between 0.79 and 0.87 at all levels of the other factors. At 10 clients each write waits for its own \texttt{fsync}, so removing it shortens every request. At 160 clients group commit already spreads one \texttt{fsync} over many requests, so removing it saves little, and our data do not show why it then costs throughput. The probes ran at 80 clients, where the reversal does not appear. There, without \texttt{fsync}, the log-sync stage flushes 1.9 requests at a time instead of 16--17, yet the leader spends the same CPU per operation (59 against 60\,$\mu$s). Explaining the reversal would need probes at 160 clients.

Five servers raise throughput by 14\% ($\times1.14$, 1\% of the variation), and the effect is significant against both errors ($\times1.08$--1.21 in the whole-plot test). The gain grows with the load (A$\times$C), from $\times1.05$ at 10 clients to $\times1.24$ at 160. It is the same at both write ratios (A$\times$B $=\times1.00$), so it cannot come from the extra servers answering more reads. One possible reason is the leader's share of the sessions, which we did not record in the factorial runs. Sessions are spread over all servers, so the leader serves a third of them with three servers and a fifth with five, and client connections take 0.4 of the leader's two cores (Section~\ref{sec:ebpf}). With fewer sessions the leader keeps more CPU for coordination, which only matters once it is saturated. The log disk (F) has no main effect under either error and appears only in a small E$\times$F interaction (0.5\%).

\paragraph{Write tail latency.} The write p99 depends mostly on load. Going to 160 clients multiplies it by 11.7 (94\% of the variation), from 2.7 to 31.7\,ms in geometric means. With sixteen times more clients and less than twice the throughput, each request simply finds a longer queue at the leader. No other effect changes the p99 by more than a third. Payload gives $\times1.32$, the write ratio $\times1.21$, \texttt{forceSync} $\times0.82$ and five servers $\times1.10$ (significant only in the whole-plot test). Reads stay fast throughout, with a median of 0.27\,ms at 10 clients and 0.68\,ms at 160.

\paragraph{Pooled against whole-plot error.} The whole-plot intervals are narrower than the pooled ones, so rebuilding the servers added no detectable variance. None of the four whole-plot interactions is detectable, D$\times$F included. With only 7 degrees of freedom, we call an effect that is significant in just one of the two tests borderline.

\paragraph{Hypotheses.} \textbf{H1} holds only at 10 clients. The main effect of D on throughput ($\times1.07$) is borderline and much smaller than C$\times$D, which changes its sign, and D lowers the write p99 by 18\%. \textbf{H2} is not supported: B$\times$D ($\times1.04$) is not detected. \textbf{H3} could not be tested: neither F nor D$\times$F is detected, but the two disks turned out to have almost the same latency (Section~\ref{sec:ebpf}), so the levels were too close. \textbf{H4} is rejected for throughput, since five servers are faster, and holds in part for the p99, which five servers raise with 10\% writes but not with 50\% (A$\times$B, $\times0.85$). \textbf{H5} is rejected for throughput, where the write ratio matters more, and holds for the write p99.

\subsection{USL curves}
\label{sec:usl}

We measured one configuration (3 servers, 128\,B, \texttt{forceSync} on, pd-ssd) at three write ratios: 0, 30 and 50\%, each at 13 client counts from 1 to 160 with three replicates per level in random order. In the notation of the course,
\begin{equation}
  X(N)=\frac{\lambda N}{1+\sigma(N-1)+\kappa N(N-1)},
\end{equation}
where $\lambda$ is the throughput of one client, $\sigma$ the contention (serial) coefficient and $\kappa$ the crosstalk (coherency) coefficient. The fit minimizes the relative error, so that a 3\% miss counts the same at 600 and at 6{,}000 ops/s. With only three replicates per level, a formula for the intervals would rest on strong assumptions, so we use a bootstrap instead. We resample the replicates of each load level, refit, repeat this 2{,}000 times and keep the middle 95\% of the refitted values. To decide whether $\kappa$ is needed, AIC and an F-test check whether it lowers the error by more than an extra parameter would by chance. If it does not, we keep the contention-only (Amdahl) model. We validate each fit by fitting $N\le64$ and predicting the three highest loads. The timers and probes below were recorded along the 30\% curve.

\paragraph{30\% writes.} Throughput rises from 2{,}165 ops/s with one client to 46{,}436 ops/s with 160 (Fig.~\ref{fig:usl}). The full USL fit gives $\lambda=2{,}082$ ops/s (95\% interval 1{,}996--2{,}169) and $\sigma=0.0385$ (0.0345--0.0414). The crosstalk term is not supported, since the Amdahl model has the lower AIC ($-241.4$ against $-239.5$), the F-test gives $p=0.72$ and 37\% of the bootstrap fits put $\kappa$ at zero. We therefore keep the Amdahl fit ($\lambda=2{,}088$, $\sigma=0.039$, Table~\ref{tab:uslcompare}), which bounds throughput by $\lambda/\sigma\approx53{,}500$ ops/s. At 160 clients the system delivers 87\% of that bound, and the efficiency $X(N)/(N\lambda)$ has fallen to 0.14, from 0.74 at 10 clients. Fitted on $N\le64$ only, the model predicts 96, 128 and 160 clients within 1.9--5.1\%.

\paragraph{50\% writes.} Here $\lambda$ drops to 1{,}426 ops/s while $\sigma$ stays at 0.037 (0.036--0.039). Again $\kappa$ is not supported ($p=1.0$), and the hold-out error is 4.1\%. A bootstrap of the difference between the two Amdahl fits gives $\sigma_{50}-\sigma_{30}=-0.002$ with a 95\% interval of $[-0.005, +0.001]$, so we detect no change. More writes make every request more expensive but leave the serialized share of the work as it was, and the ceiling $\lambda/\sigma$ falls from 53{,}500 to 38{,}200 ops/s. The curve keeps rising up to 33{,}418 ops/s at 160 clients, without a retrograde region.

\paragraph{0\% writes.} Reads alone reach 122{,}321 ops/s, with $\lambda=4{,}891$ and $\sigma=0.029$. Here $\kappa$ is supported ($p<0.001$), with the peak $N_{\max}\approx157$ at the edge of the range. But the curve has not turned down, and from 64 clients on the client was 59--70\% busy, near our 70\% limit, so we claim no retrograde region. Reads bypass the leader, so $\sigma$ here is each server's own contention, and with the client near its limit $\kappa$ may come from the client, as in Stage I.

\paragraph{Response time.} Combining the Amdahl fit with Little's law for a closed loop without think time gives
\begin{equation}
  R(N)=\frac{N}{X(N)}=\frac{1+\sigma(N-1)}{\lambda},
\end{equation}
a floor of $1/\lambda=0.48$\,ms plus $\sigma/\lambda=19\,\mu$s for every added client. Once the system saturates, each new client only adds waiting time. Because $R(N)$ is derived from the throughput fit, its match with the measured mean $N/X$ (within 3.7\%, Appendix~\ref{app:latency}) follows by construction, and the measured median and 95th percentile lie on either side of it.

\paragraph{Per-stage times.} ZooKeeper's timers on the leader along the 30\% curve are in Appendix~\ref{app:stages} (Table~\ref{tab:stages}, Fig.~\ref{fig:stages}). The intervals overlap and do not add up: the time to quorum acknowledgment starts when the proposal is created and includes the leader's own log sync and the followers' round trip. From 1 to 160 clients the server-side write latency grows from 0.87 to 5.57\,ms. The time to quorum acknowledgment grows most in absolute terms ($+2.07$\,ms), followed by the queue in front of request preparation ($+1.35$\,ms, most of it beyond 64 clients) and the time from commit to applied ($+1.11$\,ms). The log-sync queue levels off at about 0.7\,ms, because the batch grows from 1 to 17.6 requests per \texttt{fsync} (18.5 in the separate probe runs). The \texttt{fsync} timer truncates to whole milliseconds, hence its 0.06\,ms at $N=1$. A read served by the leader takes 2.79\,ms at 160 clients against 0.97\,ms on average, 1.48\,ms of it in the commit stage.

\label{sec:ebpf}

They measure \texttt{fsync} latency (syscall tracepoints), block-I/O latency per disk (block tracepoints, since bcc's \texttt{biolatency} kprobe is not traceable on kernel 6.1), run-queue latency, TCP retransmissions, and CPU per thread (a 99\,Hz \texttt{profile} probe keyed by the stage's thread name). \paragraph{The \texttt{fsync} and the disk.} With \texttt{forceSync=no} the probe sees no \texttt{fsync} at all, which confirms that factor D was applied. Along the curve an \texttt{fsync} grows from 0.55\,ms at one client to 1.1\,ms at 160, as the batch grows from 1 to 18.5 requests. At 80 clients it takes 1.0\,ms on average on both disks, and its CDF (Fig.~\ref{fig:cdf}) has two steps, with 21--27\% of the calls at 256--512\,$\mu$s and 68--75\% at 1--2\,ms. The block-I/O CDFs of the two disks almost coincide, with 85--88\% of the requests in the 256--512\,$\mu$s bucket. Neither disk is faster, which agrees with F having no effect, and a separate \texttt{fio} test (4\,KiB writes, an \texttt{fsync} after each) confirms it with 1.31\,ms per \texttt{fsync} on pd-balanced and 1.33\,ms on pd-ssd. The 2.7 block requests per \texttt{fsync} suggest that ext4 also commits its journal, which would explain the 1--2\,ms step. Without \texttt{fsync} the log disk sees only about 390 large background write-backs in 45\,s, which no request waits for.

\paragraph{CPU, scheduler and network.} The leader's JVM goes from 0.52 of its two vCPUs at one client to 1.70 at 160, mostly replication (0.58) and client connections (0.43); request preparation uses 0.25 and log sync 0.11. The run-queue p99 grows from 63 to 511\,$\mu$s, garbage collection stays under 0.003 cores, and no packet is retransmitted.

\paragraph{Probe overhead.} Probed runs differ from their unprobed neighbours by $-4\%$ to $+7\%$, within the neighbours' own spread (up to 17\%; 43\% in the 80-client set, used only for counts, distributions and CPU shares).

\section{Discussion: What Limits Scalability}
\label{sec:discussion}

  \centering

    \midrule
    $\sigma$ & The leader's CPU: replication, client connections, ordering, log sync
      & $\sigma\approx0.038$ at 30 and 50\% writes; demand $2\sigma/\lambda=37\,\mu$s/op against 38--40 measured; JVM at
        1.5--1.7 of 2 cores; no thread near a full core; D and F do not help at saturation \\

    $\lambda$ & One request alone: round trips, serialization, payload, \texttt{fsync}
      & 0.48\,ms per request; 4\,KiB payloads $\times0.74$; quorum ACK 0.72\,ms at $N=1$ (0.77 in the probe runs) \\

      & $\times1.14$, mostly at 160 clients; same at both write ratios; no retransmissions \\
    \bottomrule
  \end{tabularx}
\end{table}

\paragraph{Log sync.} Table~\ref{tab:limits} maps the USL terms to the pipeline. The log-sync stage is a single thread, so it is the first candidate for $\sigma$. At 160 clients the leader logs about 13{,}300 writes per second in batches of 18.5, which makes 720 \texttt{fsync}s per second of 1.1\,ms each. The thread is in \texttt{fsync} about 80\% of the time (86--87\% at 16 and 64 clients), but it does not cap throughput: more requests make the batch larger and the cost per request smaller, which is why neither D nor F helps at saturation.

\paragraph{Leader CPU.} No other thread comes close to a full core, which leaves the leader's CPU as a whole. The Amdahl fit caps throughput at $\lambda/\sigma\approx53{,}500$ ops/s, so the bottleneck needs $D=\sigma/\lambda\approx18.7\,\mu$s per operation. If that bottleneck is the leader's two vCPUs ($U=XD/2$), each operation needs $37\,\mu$s of CPU. The thread probe measures this directly along the curve: 40.4\,$\mu$s at 64 clients and 38.3\,$\mu$s at 160, at a utilization of 0.76--0.85. At low load fixed background work, such as heartbeats, raises the CPU per operation (285\,$\mu$s at one client), so the comparison holds only near saturation.

\paragraph{Two vCPUs and the 50\% curve.} At the asymptote, two vCPUs act like one serial server of twice the speed, so $\sigma=\lambda D_{\mathrm{CPU}}/2$. At 50\% writes the match is looser. The noisier 80-client runs give about 60\,$\mu$s per operation against 52\,$\mu$s from the fit, and their CPU cap of 33{,}000 ops/s is below the fit's asymptote of 38{,}200; the curve itself reaches 33{,}418 at 160 clients. From 30 to 50\% writes the CPU per operation grows about 1.5 times and the single-client time $1/\lambda$ about 1.46 times, so $\sigma$ hardly changes, as the bootstrap found.

\paragraph{Mitigations.} To relieve the leader's CPU: a larger machine for it, \texttt{leader\-Serves=no}~\cite{zookeeper_admin}, observers for reads, and multi-operations. A faster log disk would not help, and turning \texttt{fsync} off costs throughput at high load as well as durability.

\section{Conclusion}

Within the levels we tested, what clients do matters more than how the servers are configured: the share of writes and the load explain most of the throughput variation, the log disk none, and \texttt{fsync} only through its interaction with load. With writes the scalability curves show contention but no crosstalk, and the contention does not change between 30 and 50\% writes. Near saturation, the leader's CPU explains the bottleneck the fit implies.

\emph{Limitations.} We measured scalability against load only, with three servers, and the number of servers appears only as a two-level factor. Several of our explanations also rest on measurements we did not take. We did not record the leader's share of the sessions in the factorial runs, probe the followers, measure off-CPU time per thread, trace the ext4 journal or check the 20\,s windows for steady state. Treating two hyperthreads as two servers also overstates the leader's spare capacity. Finally, the workload has no creates or watches.
