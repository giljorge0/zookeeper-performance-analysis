\begin{abstract}
We study the write pipeline of Apache ZooKeeper 3.9, a coordination service in which reads are served locally by
any server while every write is serialized through one leader and a quorum. Stage II systematizes the
evaluation on Google Compute Engine, with the servers and the load generator on separate machines. We
(i) run a $2^{6-1}$ fractional factorial experiment over six factors (ensemble size, write ratio, number of clients,
\texttt{forceSync}, payload size and log disk) with two replicates and a randomized, blocked run order;
(ii) fit one Universal Scalability Law curve, with replicates, bootstrap confidence intervals and a test of whether
the coherency term is justified; and (iii) follow a write through the pipeline with ZooKeeper's own per-stage counters
and five eBPF probes (fsync latency, block-I/O latency, run-queue latency, TCP retransmissions and the CPU used by each
pipeline thread). We also correct two conclusions of our Stage I report: the
Stage I load generator logged every operation, which throttled it and made the contention coefficient look
independent of the number of servers, and the reported effect of network delay compared against the wrong
baseline. \todo{one or two sentences with the main findings: which factors and interactions explain most of the

\section{Introduction}

Apache ZooKeeper is an open-source coordination service used by systems such as Kafka, HBase and Hadoop for leader
election, configuration management and distributed locking~\cite{hunt_zookeeper,apache_zookeeper_overview}.
It has a clear client-server split, is genuinely distributed, and has a published replication protocol, Zab~\cite{zab_junqueira}.
We chose it because its read/write asymmetry gives a clean hypothesis: reads are answered by any server and should
scale with the ensemble, whereas every write passes through a single leader and must reach a majority, so writes
should not.

Stage I measured throughput against the number of concurrent clients on one laptop and fitted the Universal
Scalability Law (USL)~\cite{gunther_usl_dsconf,gunther_book}. Stage II asks for a more systematic
evaluation. Our contributions are:
\begin{itemize}
  \item a corrected baseline: we found and fixed a client-side artifact in the Stage I measurements
    (Section~\ref{sec:corrections}) and show how large run-to-run variation is on shared hardware;
  \item a $2^{6-1}$ fractional factorial experiment on Google Compute Engine that ranks the factors and
    interactions that drive throughput and write tail latency (Sections~\ref{sec:design} and~\ref{sec:factorial});
  \item a single, well-supported USL fit, with the time a write spends in each pipeline stage measured at every load
    level, so that the coefficients can be tied to stages of the pipeline (Section~\ref{sec:usl});
  \item five eBPF probes, four of them our own, that observe the log-sync stage, the disk, the scheduler, the network
    and the CPU of each pipeline thread from inside the kernel (Section~\ref{sec:ebpf}).
\end{itemize}

\section{System Description}

\subsection{Data model, consistency and the two request pipelines}

ZooKeeper stores a small tree of data nodes (znodes) entirely in memory and persists changes to a transaction log.
An ensemble of $N$ servers elects one \emph{leader}; the others are \emph{followers}. A client keeps a session with one
server. Writes are linearizable through Zab; reads are sequentially consistent per session and may be slightly stale,
which is what lets every server answer them alone~\cite{hunt_zookeeper}. Figure~\ref{fig:pipeline} shows both pipelines.

Inside a server a request goes through a chain of processors. The ones that matter here are request preparation
(assigns the zxid and validates the operation on the leader), the log-sync stage (appends to the transaction log and
groups \texttt{fsync} calls) and the commit stage (applies the operation once it is committed). Request preparation
and log sync are each handled by a single thread, which makes them the natural candidates for the serialized fraction
$\alpha$ of the USL. With $N=2f+1$ servers the ensemble tolerates $f$ failures and keeps serving while a majority is
reachable, choosing consistency over availability otherwise~\cite{zab_junqueira}.

\subsection{Why the write pipeline is the object of study}

A read costs one hop and no coordination; a write needs a forward to the leader, a proposal, a disk write and
acknowledgment at every follower, and a commit. Throughput of reads therefore grows with the number of servers,
while the cost of a write grows with it. The experiments of this report ask which stage of the write pipeline
limits scalability and which of the cost terms of the USL it corresponds to.

\section{Corrections to the Stage I Measurements}
\label{sec:corrections}

Before the Stage II experiments we re-examined the Stage I data and found three problems. We report them because they
change two conclusions of the Stage I report and because they shaped the design of Stage II.

\paragraph{The load generator logged every operation.}
% src: results_java_noisy.csv, results_java_v2.csv, gap_diagnosis.csv
The same configuration (3 servers, 20 clients, 30\% writes) reached 6{,}364 ops/s in the Stage I sweep but
14{,}832 ops/s when the sweep was repeated with a quiet client. A controlled comparison showed that the jar used for the
sweep printed about 145{,}000 lines in a 15\,s run, roughly one per operation: the shaded jar contained Logback, whose
default configuration logs the ZooKeeper client at DEBUG level, so all client threads queued on the output. With the
output redirected to a file, 15 interleaved runs of five variants gave 6{,}300--12{,}000 ops/s, and neither the JVM heap
flags nor the metrics collector made a consistent difference.
The fix is a one-line Logback configuration that turns logging off, and the experiment runner now aborts a run
if the client prints more than a few lines.
This invalidates the Stage I interpretation of $\alpha$. The Stage I fits gave the same $\alpha\approx0.23$ for 1, 3 and 5
servers, and we concluded that the contention was server-side but not specific to Zab. A client-side serialization
point looks exactly like that, because it does not depend on the number of servers; the constant $\alpha$ was most
likely an artifact of the client. With the quiet client the fitted $\alpha$ was 0.025, 0.088 and 0.112 for 1, 3 and 5
servers, and the standalone server no longer saturated within 80 clients (29{,}000 ops/s). We withdraw the Stage I
claim and re-measure $\alpha$ in Section~\ref{sec:usl}.

\paragraph{Run-to-run variation on a laptop is large.}
% src: gap_diagnosis.csv
In the same comparison, repetitions of an identical variant differed by up to a factor of two (6{,}285 against
12{,}043 ops/s), more than any difference between the variants. The Stage I
sweep used one run per point in order of increasing load, so drift and load were confounded, and the differences between
the three fitted curves are within this noise. Stage II therefore uses dedicated virtual machines, replicates and a
randomized run order.

\paragraph{The network-delay result was misreported.}
The ``$27\times$'' collapse under a 20\,ms delay compared the delayed run with the old Python baseline. The corrected
numbers are in Section~\ref{sec:chaos}.

\section{Testbed and Methodology}
\label{sec:method}

\paragraph{Deployment.}
All experiments of Stage II run on Google Compute Engine in one zone (\todo{confirm: europe-west1-b}). The load generator
runs on its own virtual machine (\todo{confirm: n2-standard-8}) and the ZooKeeper servers each on a separate machine
(\todo{confirm: n2-standard-2}), so that client and servers do not compete for CPU, which was a limitation of Stage I.
ZooKeeper 3.9.3 runs natively (not in a container) with a 1\,GB heap, \texttt{tickTime}=2000\,ms and no client-connection
limit. Each server has two extra disks, pd-balanced and pd-ssd, and the transaction log (\texttt{dataLogDir}) is placed on
one of them according to the factor \emph{log disk}; snapshots stay on the boot disk. Before each block of runs the
servers are stopped, their data and logs are wiped and they are restarted with the levels of the block.
The deployment is scripted (Compute Engine only, no Kubernetes) and the servers are configured over ssh.

\paragraph{Load generator.}
The benchmark is a multi-threaded Java client built on an \texttt{ExecutorService} with one ZooKeeper session per
concurrent client; the connect string lists all servers, so sessions spread across the ensemble. Each client is a closed
loop of synchronous calls with no think time: it picks a znode uniformly from a pool of 200 znodes created before the
run, and issues a \texttt{setData} with probability equal to the write ratio and a \texttt{getData} otherwise.
All sessions are connected before a barrier releases them together, so connection time never enters the warm-up or the
measurement. Operations that start during the 5\,s warm-up are executed but not recorded. Latencies are recorded per
thread, merged at the end, and percentiles are computed exactly by sorting. Throughput is the number of successful
operations divided by the measurement window; failed operations are counted by exception type and excluded.

\paragraph{Run protocol and checks that the client is not the bottleneck.}
During every run the client machine samples its own CPU utilization (\texttt{vmstat}, once per second, over the measured
window); a run with a client above about 70\% busy would measure the client and not ZooKeeper. The runner also aborts if
the client prints more than a few lines of output (Section~\ref{sec:corrections}), and verifies on every server, before
the first run of each block, that the server-side factors were really applied: the \texttt{forceSync} flag in the
arguments of the running JVM and the directory of the transaction log reported by the server itself.

\paragraph{ZooKeeper's own view of the pipeline.}
ZooKeeper~3.9 keeps a summary per pipeline stage (count and sum of, for example, the time a request waits for the
request-preparation thread, the time it waits for and spends in the log-sync stage, the number of requests written per
\texttt{fsync}, the \texttt{fsync} time and the time until a quorum has acknowledged a proposal) and reports them through
the \texttt{mntr} command. Around every run of the USL sweep and of the probe runs we take a snapshot of every server;
the difference of two snapshots divided by the difference of the counts is the mean of that stage over that run alone.
These timers have a resolution of 1\,ms (the \texttt{fsync} time is truncated to whole milliseconds), which is why the
\texttt{fsync} is also measured with eBPF in microseconds.

\paragraph{Evaluation process.}
The evaluation is three experiments, all scripted (\path{gce/vm_jobs.sh}) and all with their raw data in the
repository: (1) the factorial experiment of Section~\ref{sec:design}, 64 runs in a randomized, blocked order that is fixed
before the first run (\path{factorial/plan_gce/plan.csv}); (2) one USL curve, 13 load levels with three replicates in
random order, with the per-stage counters around every run (Section~\ref{sec:usl}); (3) the probe runs, one per
combination of \texttt{forceSync} and log disk, each paired with an identical run without probes to measure their
overhead (Section~\ref{sec:ebpf}). The analysis scripts were validated on synthetic data with known effects before they
were applied to measurements.

\paragraph{Threats to validity.}
Virtual machines on a shared cloud have neighbours we cannot control; replicates and randomization are our defence.
The servers are in one zone, so inter-server round trips are far shorter than in a geo-replicated deployment. Disabling
\texttt{forceSync} is not a safe production setting and is used only as an experimental probe.

\subsection{Metrics}

The primary metric is \emph{throughput} (successful operations per second), because the USL is a model of throughput. The
secondary metric is the \emph{99th percentile write latency}: coordination services sit on the critical path of other
systems, so the tail of the write path matters as much as its rate. Read latency is recorded but is not a response of
the design, because reads never leave the server they are sent to. The mean latency is not a response either: in a closed
loop without think time, Little's law gives a mean response time of $R=N/X$ for $N$ clients, so it carries no information
beyond the throughput, whereas the 99th percentile does. Two further quantities are recorded in every run as validity
checks, not responses: the number of failed operations and the CPU utilization of the load generator.

\subsection{Factors and levels}

Each factor is tied to a hypothesis from Stage I about where the cost of the write pipeline sits
(Table~\ref{tab:factors}). The low level of the number of clients (10) lies below the saturation knee measured in Stage I and
the high level (160) lies well beyond it; the write ratio 0.1 is close to the production ratio of about 10:1
cited in~\cite{mit_6824_zookeeper} and 0.5 stresses the write pipeline. Disabling \texttt{forceSync} removes the log-sync
stage from the write path; it is a controlled probe, not a recommendation. Ensembles of three and five servers are the two
sizes used in practice (they tolerate one and two failures). The payloads bracket small metadata (128\,B) and
configuration blobs (4\,KiB), far below the 1\,MB limit of a znode. pd-balanced and pd-ssd are the two Persistent Disk
types a dedicated log device would realistically use; Persistent Disk performance grows with the size of the disk and of
the machine, so with 20\,GB disks on two-vCPU servers these are levels of this testbed rather than of the disk types in
general.

\subsection{Design}

A full $2^6$ design needs 64 runs per replicate. We use a half fraction, $2^{6-1}$, generating the sixth factor as
$F=ABCDE$, i.e.\ with the defining relation $I=ABCDEF$~\cite{jain_book}. The design has resolution VI: every main effect is
aliased only with a five-factor interaction and every two-factor interaction only with a four-factor interaction;
three-factor interactions are aliased in pairs. Assuming that interactions of order four and higher are negligible, all six
main effects and all fifteen two-factor interactions are estimated cleanly from 32 runs per replicate
(Table~\ref{tab:alias}). With two replicates the experiment has 64 runs and 32 degrees of freedom for the error, which
gives confidence intervals on every effect. The full sign table is in Appendix~\ref{app:sign}.

\paragraph{Why this fraction, and how the sign table is built.} A full $2^6$ design would need 128 runs for two replicates;
the half fraction needs 64 and loses nothing we intend to estimate, because what it confounds with the main effects and
two-factor interactions are interactions of order five and four. A quarter fraction ($2^{6-2}$, 16 runs per replicate)
would have resolution IV: two-factor interactions would be aliased in pairs, and that is exactly where hypotheses H2--H4
sit. The sign table is the full $2^5$ table of factors A--E with the column of F computed as the product $ABCDE$ of the
other five; every column is balanced and orthogonal to all others (checked by \texttt{design.py}). The effect of a factor
or interaction is the inner product of its column of signs with the 32 run means, divided by 32; the column of an
interaction is the product of the columns of its factors. The plan, with its run order, was generated with a fixed seed
before the first run and is part of the repository.

\paragraph{Restricted randomization.} Ensemble size, \texttt{forceSync} and log disk require restarting and reconfiguring the
servers. Runs that share the levels of these three factors form a \emph{block} (eight blocks of four runs per
replicate, so 16 server rebuilds instead of 64). The order of the blocks is randomized independently in each replicate and the order of the runs inside a
block is randomized as well. Because every replicate rebuilds the servers from scratch, restart-to-restart variability enters
the pure-error estimate. This is not a full split-plot analysis: a proper one would test the three hard-to-change factors
against a separate whole-plot error with fewer degrees of freedom, so their confidence intervals may be somewhat
optimistic. We therefore interpret them mainly by their share of the variation and treat only large effects as conclusive.

\subsection{Analysis method}

Let $s_{ij}$ be the $\pm1$ entry of the sign table for run $i$ and effect $j$, $\bar y_i$ the mean of the $r$ replicates of
run $i$ and $n=32$ the number of runs. The effects, the allocation of variation and the confidence intervals are
\begin{equation}
  q_j=\frac1n\sum_{i} s_{ij}\,\bar y_i,\qquad
  SS_j=n\,r\,q_j^2,\qquad
  SSE=\sum_{i,k}(y_{ik}-\bar y_i)^2,
\end{equation}
\begin{equation}
  SST=SSE+\sum_j SS_j,\qquad
  s_e^2=\frac{SSE}{n(r-1)},\qquad
  q_j \pm t_{[0.975;\,n(r-1)]}\,\frac{s_e}{\sqrt{n\,r}} .
\end{equation}
The share of the variation explained by effect $j$ is $100\,SS_j/SST$. With 31 effects tested at the 95\% level about two
false positives are expected, so effects are ranked by their share of the variation and not only by significance. We check the
residuals against the predicted value and on a normal quantile plot; if the ratio between the largest and the smallest response
exceeds 10, the analysis is repeated on $\log_{10}$ of the response (a multiplicative model). The analysis code was validated on
synthetic data with known effects before it was applied to measurements.

\subsection{Hypotheses}

We fix the expected outcomes before running, so that the experiment can falsify them.
\begin{itemize}
  \item \textbf{H1 (log-sync stage).} Disabling \texttt{forceSync} (D) increases throughput and lowers the write p99 latency;
    the eBPF fsync probe shows (almost) no fsync calls when D is at its high level. If D has no effect, the contention
    coefficient $\alpha$ does not come from the fsync.
  \item \textbf{H2 (writes).} The benefit of disabling fsync grows with the write ratio (interaction B$\times$D), since reads never
    touch the log.
  \item \textbf{H3 (disk).} A faster log disk (F) helps only while fsync is on (interaction D$\times$F).
  \item \textbf{H4 (quorum).} A larger ensemble (A) lowers throughput and raises the write p99 latency, concentrated in writes
    (interaction A$\times$B).
  \item \textbf{H5 (load).} The number of clients (C) has the largest main effect on throughput, because its low level is below and
    its high level above the saturation point.
\end{itemize}

\subsection{One USL curve}
\label{sec:usl}

Following the feedback on Stage I we fit a single curve instead of one per ensemble size, and make it a well-supported one:
one configuration (3 servers, write ratio 0.3), thirteen client counts from 1 to 160, three replicates each in random order, on dedicated
machines, with the weighted fit and the bootstrap, Amdahl-comparison and hold-out checks described below. The effect of the
ensemble size is not read from separate fits but measured as factor A of Section~\ref{sec:factorial}.
The model is
\begin{equation}
  X(N)=\frac{\gamma N}{1+\alpha(N-1)+\beta N(N-1)},\qquad N_{\max}=\sqrt{(1-\alpha)/\beta},
\end{equation}
where $\gamma$ is the throughput of one client, $\alpha$ the contention coefficient (the serialized fraction of the work)
and $\beta$ the coherency coefficient (the pairwise cost of keeping participants consistent, which produces retrograde scaling).
The fit minimizes the relative error, so that a 3\% error counts the same at 600 and at 6{,}000 ops/s; confidence intervals come from a
bootstrap over the replicates; the full model is compared with the contention-only (Amdahl) model by AIC and an F-test, so that
$\beta$ is claimed only if the data justify the extra parameter; and a fit on the lower loads is used to predict the highest ones.

\subsection{eBPF probes}
\label{sec:ebpf}

Five probes observe the leader's operating system while the benchmark runs; four are our own bpftrace
programs~\cite{gregg_bpf} and one is a bcc tool. Each is aimed at one suspected limit of Table~\ref{tab:limits}.
\begin{itemize}
  \item \textbf{fsync latency} (ours): tracepoints \texttt{syscalls:sys\_enter/exit\_fsync} and \texttt{fdatasync}, filtered to the
    ZooKeeper JVM. Number of calls and latency histogram of the log-sync stage, in microseconds. With \texttt{forceSync=no}
    it must see (almost) no calls, which also verifies that factor D was applied.
  \item \textbf{Block I/O latency} (ours, per disk): tracepoints \texttt{block\_rq\_issue} and \texttt{block\_rq\_complete}.
    Whether the log disk itself is slow underneath the \texttt{fsync}; compared between pd-balanced and pd-ssd. (We first
    used bcc's \texttt{biolatency}, but its kprobe, \texttt{blk\_account\_io\_done}, is not traceable on the 6.1 kernel
    of the servers.)
  \item \textbf{Run-queue latency} (bcc \texttt{runqlat}, threads of the JVM only): scheduler tracepoints, from wake-up to
    running. Whether the server waits for a CPU, which would add to $\alpha$ independently of the disk.
  \item \textbf{TCP retransmissions} (ours): the \texttt{tcp} tracepoints \texttt{tcp\_retransmit\_skb} and
    \texttt{tcp\_send\_reset}. Whether packet loss adds retransmission timeouts to the round trips of the quorum.
  \item \textbf{CPU per pipeline thread} (ours): a 99\,Hz \texttt{profile} probe filtered to the JVM and keyed by thread name.
    ZooKeeper runs each stage in a named thread (request preparation, log sync, commit, client connections) and the JVM
    passes the names to Linux, so this is the CPU used by each stage; a single-threaded stage close to one full core is a
    serialized bottleneck.
\end{itemize}
The probes run in separate runs of a saturating configuration (3 servers, 80 clients, write ratio 0.5), at both levels of
\texttt{forceSync} and of the log disk, never during the factorial runs. Every probed run is paired with an identical run
without probes before it and another after it (the overhead is measured against their mean, after a discarded warm-up
run), and ZooKeeper's counters are read around it (Table~\ref{tab:ebpfzk}).

\subsection{Leader failover}
\label{sec:failover}

With a continuous benchmark running against a 3-server ensemble we identified the leader with the \texttt{stat} command and killed
its container. The two survivors kept a majority and continued serving, and ZooKeeper logged the re-election:
\texttt{FOLLOWING - LEADER ELECTION TOOK - 211 MS} in the first run, and 216\,ms (follower) and 235\,ms (new leader) in a repetition. This is
ZooKeeper's own measurement of the election phase, not the outage seen by a client, which also waits for its retry and reconnect
logic and which we did not instrument. \todo{optional: repeat on Compute Engine and measure the client-observed gap between the last
successful operation before the kill and the first one after it.}

\subsection{Network delay}
\label{sec:chaos}

To see how the model behaves under a large increase of the service time per request, we injected a 20\,ms$\pm$2\,ms delay with
Pumba~\cite{pumba}, which drives \texttt{tc netem}, on the egress of every server container of the Stage I ensemble (the delay is applied
inside each container's network namespace, because a delay on the Docker bridge does not affect traffic between containers) and re-ran the
sweep with the corrected client (Table~\ref{tab:chaos}).

\begin{table}[t]
  \centering
  \caption{Throughput (ops/s) with and without a 20\,ms egress delay, 3 servers, Stage I laptop, one run per cell.}
  \label{tab:chaos}
  \footnotesize
  \begin{tabular}{@{}lrrrrrr@{}}
    \toprule
    Clients & 1 & 5 & 10 & 20 & 40 & 80 \\
    \midrule
    No delay      & 2386 & 7016 & 11680 & 14832 & 16238 & 16255 \\
    20\,ms delay  & 20.6 & 108.9 & 216.7 & 434.6 & 865.5 & 1709 \\
    Ratio         & 116$\times$ & 64$\times$ & 54$\times$ & 34$\times$ & 19$\times$ & 9.5$\times$ \\
    \bottomrule
  \end{tabular}
\end{table}

With one client throughput falls $116\times$ (not $27\times$ as reported in Stage I, which compared with the Python baseline), but at 80
clients it falls only $9.5\times$. Throughput per client is constant at about 21.5 ops/s, one operation every 46.5\,ms: a closed-loop client
completes one operation per round trip, and $N$ clients in parallel complete $N$ operations as long as the server is not busy. The fitted $\alpha$
and $\beta$ are therefore near zero: the delay hides the server, and the saturation point has moved beyond the loads we tested. $\alpha$ and
$\beta$ describe the regime that was measured and are not constants of the system. The latencies give a direct view of the write pipeline: the
median read takes 22.7\,ms, one delayed hop (the reply), and the median write takes 106\,ms, about five delayed hops (forward to the leader,
proposal, acknowledgment, commit, reply), which is what Figure~\ref{fig:pipeline} predicts for a client attached to a follower.

\section{Discussion: Which Parts of the Pipeline Limit Scalability}
\label{sec:discussion}

Each term of the USL corresponds to a part of the write pipeline (Table~\ref{tab:limits}). Reads are different: a read is answered
by the server the client is attached to without any coordination, so reads are limited by that server's CPU and not by the leader.
In the curve of Section~\ref{sec:usl}, $N$ is the number of clients and the ensemble is fixed at three servers, so the cost of
the quorum per write (one proposal to each follower, a majority of acknowledgments, a commit) does not change with $N$: it is
part of $\gamma$, and of $\alpha$ where it is serialized, but it is not what $\beta$ measures. The effect of the number of servers
is measured separately, as factor A of the factorial experiment, and appears in the last row of the table.
